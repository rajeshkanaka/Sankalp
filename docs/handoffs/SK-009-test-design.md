## Semantics to freeze

- Preferences are per journey. Default disabled; enabled requires one to eight distinct integer offsets in −1440..0. Quiet hours require both valid minute-precision wall times; equal start/end is invalid. Quiet membership is `[start,end)` in the session's snapshotted journey timezone, wrapping midnight when start > end. Suppress, never shift. Preview evaluates the intended reminder instant, including its actual civil date and DST offset; dispatch also checks quiet hours at actual dispatch time.
- Generate only intended instants strictly after the mutation clock. An existing generated job is due when `scheduled_at <= now < expires_at`, where `expires_at = min(scheduled_at + 5 minutes, session.closes_at)`. Bound total attempts to three. At the exact expiry/close boundary, expire without dispatch. Past offsets on enable/register/revise are skipped and explained in preview; do not create historical sends.
- Snooze requires an enabled journey, active device and open, incomplete session. Target `now + 10 minutes` must be strictly before close and outside quiet hours. Reject an ineligible snooze with a reason. Atomically cancel not-yet-dispatched reminders for that session/device with intended times in `[now,target]`, then create one snooze per active device using the request operation ID. Preserve earlier attempt facts; repetition of the same operation returns the original result.
- Accepted means accepted by the push service; uncertain means transmission may have occurred. Neither implies display. History read and authenticated click-open are separate idempotent facts. Completion/disable/archive/delete/revision cancels pending work; a dispatch already started may still settle accepted/uncertain and must retain both cancellation timing and actual outcome.

```sql
app.claim_reminder_jobs(p_now timestamptz, p_limit integer)
  RETURNS TABLE(job_id uuid, lease_token uuid, lease_until timestamptz);

  RETURNS reminder_settlement_result;

  RETURNS integer;
```

All functions use fixed `search_path`, explicit worker session-user checks, PUBLIC/anon/authenticated/app_api EXECUTE revocation and a restricted worker login. Clamp claim/sweep limits to 50 and leases to 60 seconds. Return server-only dispatch material only after lease/current state validation. Production worker supplies one real clock; only guarded local/CI runtime accepts the existing file clock. Do not expose these clock-bearing functions through an authenticated browser endpoint. Settlement accepts an allowlisted result/code, never arbitrary event JSON; identical settlement retry is idempotent, stale or mismatched token/attempt cannot alter a newer attempt. An expired lease with a started, unsettled attempt records uncertainty before any bounded retry. Renewal cannot resurrect an expired lease or canceled job.

Application service interfaces use existing `withUser` and `idempotent` wrappers, not worker credentials:

```text
updateReminderPreferences(userId, journeyId, {operationId, baseRevision, preferences})
  -> {preferences, revision, preview}
registerSubscription(userId, {operationId, subscription, deviceLabel}) -> safe device DTO
revokeSubscription(userId, subscriptionId, {operationId, baseGeneration}) -> safe device DTO
```

The snooze response includes per-device outcomes and uses the canonical session revision after locking. Changed preference bases/generations return reviewable conflicts; same operation ID with a different request hash returns existing `OPERATION_REUSED`. Registration, replacement, preferences and schedule activation/revision call one transaction-local generation/cancellation routine. Completion uses its existing session transaction to cancel jobs; undo never resurrects expired jobs or automatically sends missed reminders. Deletion eventually follows the approved account deletion contract; no deletion subsystem is introduced by SK-009.

## Locking and integration order

1. Preserve current account privacy advisory lock (`hashtextextended(owner,2)` shared for normal work), then existing operation-receipt lock (`seed0`) for user mutations. Never upgrade a held account shared lock to exclusive. Deletion takes its exclusive privacy lock before other locks.
2. Lock affected journeys in stable ID order; active sessions in `(opens_at,id)` order; preference rows; subscription rows in ID order; jobs in ID order. Subscription changes affecting several journeys discover and lock those journeys first. Serialize same-account subscription registration/cap enforcement with one separately allocated account-device advisory lock taken **before journey locks**; the coordinator must reserve its seed. Every path taking this new mutex follows the same position. Cross-owner endpoint reuse must not require locking a second owner's journey; revoke the stale binding atomically and let generation/owner revalidation invalidate its pending work.
3. Claim is an isolated, short job-only `FOR UPDATE SKIP LOCKED` transaction; commit before revalidation. Revalidation reacquires the normal account → journey → session → preferences → subscription → job order, fences its lease and records the attempt/dispatch start atomically. Commit before external HTTP. Keep at most four sends active. Revalidate immediately before each dispatch; do not prepare 50 dispatches and send them long after checking.
4. Settlement locks through the same order when it changes subscription eligibility (410) or dependent jobs. Cancel-before-dispatch produces no attempt. Cancel-after-dispatch preserves the attempt and records its outcome; never rewrite an accepted fact to canceled. Closure uses the existing session lock and closure key with `occurred_at=closes_at`, and a distinct recording timestamp, even with reminders disabled or no subscription. A correction still materializes closure first.

Integration prerequisites: freeze these contracts, migrate role/schema and update the two existing history guards, then add preferences + transactional job generation/cancellation and prove real SQL boundaries. Only then assign SK-010 device controls and SK-011 dispatch/history in parallel. A worker-local test never satisfies the integrated task gate.
