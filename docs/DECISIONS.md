## D01 — One web application and one reminder worker

Use a mobile-first **Next.js App Router / React / TypeScript** PWA, with CSS Modules and shared CSS variables. Use managed **Supabase Auth and PostgreSQL**, a small separately runnable **Node.js worker**, and a durable PostgreSQL job table. Use **npm**, one package/lockfile, SQL migrations and `pg` transactions; Supabase JS/SSR clients handle authentication. No ORM, Redis, separate frontend API service, realtime subscription dependency, native app, AI SDK, or agentic application runtime.

This follows the existing specification's direction while making it definite. Managed email-link auth avoids implementing identity. PostgreSQL supplies transactions and durable jobs. A continuous worker supports minute-level dispatch without tying reminders to browser tabs or request execution. Plain React/CSS keeps the calm design editable without a large UI framework. Browser IndexedDB with `idb` is added only for the required offline queue. Temporal's polyfill is used consistently for explicit timezone resolution; native Temporal availability is not assumed.

## D03 — Data access and security boundaries

Use same-origin route handlers and server-only `pg` transactions. Browser clients use Supabase for auth only; do not grant browser roles direct access to application tables. Migrations create an `app_api` database login/role with only required table/function privileges and RLS; it has no BYPASSRLS, superuser or schema-owner rights. Each request verifies the Supabase user on the server with `getUser`, then starts a transaction, sets the verified subject via transaction-local claims, and uses RLS based on that subject. Always commit/rollback before releasing a pooled connection. Never accept the claims/owner from a request body. `auth.uid()` reads the transaction-local claims. Explicit GRANTs are required; RLS alone is insufficient.

The migration owner is an offline administrative credential. The worker role can execute narrowly scoped claim/revalidate/settle/closure/deletion functions, with fixed search paths; it cannot read reflections or arbitrary user tables. Supabase admin credentials are isolated to account deletion/auth administration and local synthetic-data setup. Runtime account deletion remains server-only. Private routes are dynamic and `no-store`; neither shared caches nor the service worker store authenticated HTML/API responses.

## D04 — Schedule and product clarifications

These clarify the existing specification and are included in the requested approval. They are not approved changes yet.

1. Keep all existing launch features and A01–A27. English UI at launch; arbitrary Unicode practice names/reflections, including Devanagari. Audience is individual adult practitioners; no child/family, social or religious-advice model is introduced.
2. Start custom journeys blank. One session slot per journey; independent morning/evening practices use separate journeys. Start activation requires at least one session whose window has not opened; past reminder offsets are skipped. The fixture/test clock may make a same-day session open for deterministic demos.
3. **Partial means any nonzero recorded progress** on a required practice, or all targets met without confirmation. Thus 5/20 minutes remains Partial after closing, not Missed. An all-zero/unconfirmed checklist is Open then Missed. This resolves the numeric-progress ambiguity in specification §5.2; no partial completion credit is added.
4. Windows use a chosen **local wall-clock duration**, 1–1,439 whole minutes. Compute nominal closing local datetime, resolve both boundaries, then reject nonpositive, ≥24 elapsed-hour, or overlapping windows. Repeated local times choose the first occurrence; nonexistent times resolve to the first valid instant after the gap. Do not substitute Temporal's default gap-shift behavior (02:30 → 03:30) for the required first valid 03:00. Record/preview every adjustment.
5. All practices are required at launch. Checkbox values are booleans; repetition/minute targets are positive integers up to 1,000,000/1,439 respectively, recorded values are integers 0–1,000,000. Title 1–120 chars, intention ≤4,000, practice name 1–120, reflection ≤20,000, custom mood ≤40, maximum five mood tags. Trim surrounding whitespace; preserve Unicode and internal text. No arbitrary HTML.
6. Reminder offsets are signed minutes in [−1,440, 0], up to eight unique offsets per journey; disabled by default. Quiet hours use the journey zone, allow crossing midnight, and suppress rather than move reminders. Snooze is the separately identified +10-minute job, permitted only strictly before closing. Up to five active device subscriptions and 20 active journeys per account keep launch workloads bounded; archived history remains available.
7. Superseded sessions remain tombstones for linked reminder history. Use partial unique indexes on `(journey_id, practice_date)` and `(journey_id, ordinal)` **where not superseded**, preserving historical IDs. New schedule versions cannot change opened sessions, even if nobody visited them.
8. Reminder job identity includes session, schedule version, **reminder preference revision**, subscription generation and offset/kind. Snoozes have a distinct idempotent request key. Dispatch revalidates all generations. Click reporting proves a received application click report, not externally verified reading.
9. Optional journey-closing reflection is an **export-time text field** only, not a second persistent journal model. Private reflections are plain text. Mood tags remain optional. Export defaults exclude reflections until selected.

## D08 — Privacy and retention

No advertising/behavioral analytics or AI processing of reflections. Retain user-visible history while the account exists; journey deletion removes its content-bearing events. Operational logs are separate, redacted and expire within seven days. Deletion immediately disables access/pending sends, deletes primary owned content within 24h, and targets backup expiry within 30 days. Supabase Pro's documented seven-day daily-backup availability does **not** independently prove end-to-end erasure from all provider systems. SK-016 must establish the actual provider retention/deletion policy and any needed contract/disclosure before external beta. Unresolved compliance is a release blocker, not permission to silently weaken the promise.

The independent ledger is a private S3 bucket (separate staging/production prefixes), with public access blocked, TLS-only policy and default server-side encryption. Each object contains only opaque account UUID, deletion operation UUID and accepted deletion time; never names, email or spiritual content. Database deletion first atomically disables access/sends and writes an outbox item. A narrowly scoped server credential conditionally writes the immutable ledger object (`If-None-Match: *`) and verifies its receipt before primary/auth cleanup completes; retry is idempotent. A ledger outage preserves the disabled state and triggers the 24-hour cleanup failure alert, never a false deletion-complete message. Database restoration cannot roll this bucket back.

Worker ledger credentials are limited to the designated prefix; separate operator read/list credentials restore deletions before reopening any recovered database. Use no object versioning/replication; schedule expiry at 29 days, add an explicit daily expiry sweep and verify logical removal by 30 days. S3 Lifecycle processing is asynchronous, so do not claim its rule alone guarantees a hard physical-erasure deadline; provider retention still requires B03 confirmation. Local/CI uses a visibly simulated filesystem ledger **outside the reset database**, testing the same receipt/failure contract; real S3 policy/restore/expiry is required in SK-016/018. Missing authoritative ledger blocks reopening restored data. This small store is necessary for safe recovery after account deletion; it is not a general storage service for the app.

Production privacy text must disclose actual policies, local storage limits, reporting-based accountability, notification limitations and support contact. No end-to-end encryption claim.
